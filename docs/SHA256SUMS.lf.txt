# SHA256SUMS.lf.txt -- companion manifest: TEXT FILES ONLY, digests AFTER CRLF->LF normalisation.
#
# WHY THIS FILE EXISTS
#   .gitattributes marks text files with `text=auto`. Git therefore stores them with LF endings,
#   while a Windows checkout -- and the release zip, which is built from this working tree --
#   can carry CRLF. The bytes differ, so one file legitimately has two digests.
#   SHA256SUMS.txt records the on-disk bytes. This file records the LF-normalised bytes.
#
# DELIBERATELY LIMITED TO TEXT
#   Binaries are NOT listed here, on purpose. A .dll packed with the byte pair 0x0D 0x0A uses it
#   as machine code, not as a line break; normalising it would produce a digest for a file that
#   does not exist, and could mask a single-byte modification. Every binary must be checked
#   byte-exact against SHA256SUMS.txt, always. Only text files can differ by line ending alone.
#
# WHICH FILE TO USE
#   - Unzipped a release archive?          use SHA256SUMS.txt   (byte-exact shipped content)
#   - Cloned the repo and got LF endings?  this file covers the text files that differ
#   - Running `sha256sum -c` by hand?      pick the one matching your checkout's line endings
#
# FORMAT
#   Identical to SHA256SUMS.txt: `<64 hex>  <path>`, paths relative to the repository root,
#   forward slashes, '#' lines are comments. A standard `sha256sum -c` reads this file too.
#
# verify-kit-manifest.ps1 checks SHA256SUMS.txt first (byte-exact, every entry). Only entries that
# fail there are looked up in this file, and a hit is reported as CRLF-ONLY -- content identical,
# line endings differed -- never as a pass over tampered bytes.
