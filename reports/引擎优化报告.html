NInfer 引擎优化报告

RTX 5070 Ti 16 GB · sm_120a · 引擎 ninfer-serve-120a.exe（1,329,240,576 B / E3E0486A…）· 实测 2026-10-11
★ 2026-10-19 增补：两条新优化
1. 关掉 KVMem 环（移除 NINFER_KV_WINDOW）—— 本档池容量等于逻辑上下文上限，环永远没有降级目标，纯属空转。实测引擎显存 -186 MiB、 冷 prefill 1.59k → 1.63~1.66k tok/s、命中时 TTFT 98 → 70 ms，前缀复用率不变（99.9% → 99.9%）。
2. 切到 hybrid 前缀缓存 + 优雅关闭 （--use-alt-prefix-caching --prefix-cache-file）—— 退出时把 KV 块存盘、启动时读回。重启后首轮 11.8 s → 0.16 s（18,241 token，100% 命中）； 池仍 184,320、host 内存 4 GiB 不变。前提是从托盘正常退出 —— 引擎的优雅退出只认 CTRL_BREAK，且信号必须 AttachConsole 才送得到（托盘已改）。
代价：缓存文件 0.6~1.2 GiB 磁盘；强杀 / 断电不写盘（只是退回上次保存的版本，不会坏）。

4. 怎么用

主用（吞吐档）：双击 start-dflash-128k-tuned.bat → 引擎在 8094。
需要腾显存（浏览器/壁纸引擎/游戏在跑）：双击 start-mtp-slim.bat → 多 ~1 GiB 显存，解码 180 tok/s（两档思考强度均已对齐为 low）。
启动后照旧：start-hermes-proxy.bat（代理 8096）→ Hermes 指向 http://127.0.0.1:8096。
KVMem 生效判据不变：stderr 出现 kvmem_score: SELECT 或 ring retrieve 行。

7. Vision 驻留位置实测（默认挂在 GPU，不是 CPU）

引擎 --vision 的默认角色是 resident（--help 原文：accept images and video and load the Vision GPU allocations）。只有显式给 --vision-residency 才会离开设备内存。mtp 档此前只写了 --vision，所以视觉塔一直常驻显存。
同参对照（mtp 模型，各跑 2 轮；Δ = 加载后显存 − 桌面基线）：
配置 ΔVRAM（2 轮） runtime free
只给 --vision（默认 resident）13856 / 13940 MiB2.39 GiB~1.02 GiB
--vision-residency overlay（已采用）13259 / 13318 MiB2.07 GiB~1.50 GiB
--vision-residency cpu（tuned 档）13256 / 13270 MiB2.07 GiB~1.58 GiB
完全去掉 --vision13278 / 13239 MiB2.06 GiB~1.55 GiB
结论：默认 resident 多占约 600 MiB；overlay / cpu / 关闭三档在本卡上几乎等价（差异在噪声内）。start-mtp-slim.bat 已改为 overlay——拿回这 600 MiB，而 不牺牲图片分辨率：cpu 会把 --vision-max-merged 隐式压到 256（除非显式给值），tuned 档正是这种情况；overlay 保留 16384 默认。
端到端复核：经桌面快捷方式启动，6 秒就绪，Δ 13262 MiB、free 1491 MiB。
代价：视觉处理走 CPU 侧、稍慢；发大图时会临时借用设备显存。若你从不发图片，可直接删掉 --vision，省的显存一样多且不加载视觉塔。

视觉功能端到端验证（2026-10-11）：用一张 512×512 判分图（白底 + 红圆 + 蓝方块）分别向 tuned 与 slim 发送 base64 图片请求，两档均 HTTP 200 且识别正确（回答 "Two shapes: a red circle and a blue square."）。overlay 未破坏视觉功能，图片被正常预处理（media 1, prepared ~5 ms）；cpu 的 256 压缩在常规图片上不影响识别，仅细节损失。

8. Hermes 长会话崩溃（worker crash）的诊断与修复

现象（2026-10-11 用户截图）：Hermes 用了一段时间后，引擎窗口打印 worker crash: Paged KV reservation invariant was violated 与 req#15 failed ... HTTP 500；Hermes 侧表现为"AI 服务返回了无法读取的回复"。
adopt host-backed: frontier=33402 need=522 usable=280 host_backed=390 demote-other short: freed=0 want=390 slots=1 invalid=0 n=0 stale_epochs=0 dup=0 flushfree ERROR engine | worker crash: Paged KV reservation invariant was violated ERROR req#15 failed during generation | HTTP 500 | internal error
根因：两个启动器此前被设成 NINFER_KV_REUSE_HOSTBACKED=1。该模式在追问时会把 ring 里保留的 host-KV 前缀 整体 adopt 进活动 KV；当会话长到超过设备池（本次 prompt 51,944 token > 池 17,920）时装不下 → demote 也腾不出（freed=0）→ 触发引擎内部 "Paged KV reservation invariant"，worker 直接崩溃。
修复：两个启动器改回 NINFER_KV_REUSE_HOSTBACKED=0（这本来就是 fix-summary.html 与 README-128k.txt 在 2026-10-10 记录的同一处方）。KVMem ring 与内容打分保留，代价是每轮重新 prefill（追问变慢，但不再 500、不再崩溃）。
别把两件事混为一谈：
  ① 崩溃 / 500 = REUSE=1 的 adopt 失败 → 处方：改回 0；
  ② 静默答错 = 超池时"中段内容消失、HTTP 200 但答案是错的" → 治它的是 KVMem 内容打分（判据：日志出现 kvmem_score: SELECT 行）。超池本身不等于崩溃，但"超池 + REUSE=1"会崩。
另一个提醒：会话 52k token 时，即便不崩，每轮重 prefill 也会明显变慢；若长期如此使用，建议在 Hermes 侧收敛历史长度与工具数量（本次请求是 42 messages + 27 tools + 5 media）。

9. "思考了但不输出" —— 无限思考把答案饿死（已修复）

症状：客户端里看到模型在思考（reasoning 流出来了），但最终答案一个字都没有。
根因：思考 token 与答案共用同一个 max_tokens 预算，引擎默认又没有给思考单独设上限。在一道难题上（--default-reasoning-effort high），模型把整个 32768 输出预算全烧在思考里，正文 0 字符、finish_reason=length。
档位 耗时 思考 token 正文 finish
none58 s015873 字 ✅stop
minimal236 s32768（烧光）0length
low238 s32768（烧光）0length
medium116 s177730stop
high273 s32768（烧光）0length
结论：只要开思考，这个模型在这种难题上就会"想不完、不落笔"——降档位解决不了（low/minimal 同样烧光）。
解药是引擎自带的两个开关（两个启动器均已加入）：
  --default-thinking-budget 2048 —— 给思考设独立上限；
  --thinking-budget-message "..." —— 到预算时注入提示，引擎自动补上思考闭合标记，逼模型转入正文。
修复后实测（同题同档 high）：修复前 273 s / 正文 0 字 → 修复后 20 s / 正文 769 字，答案正常给出。
一个必须记住的约束：思考预算必须明显小于客户端给你的 max_tokens，否则思考照样吃光配额。实测：
  客户端 max_tokens 32768（或不传，用引擎默认）→ 思考预算 4096/2048 都正常；
  客户端 max_tokens 2048 → 思考预算必须降到 1024（2048 会失败、正文为空）。
所以：你的客户端如果固定了一个很小的 max_tokens，请把两个启动器里的 --default-thinking-budget 改成 1024。简单题不受影响（实测思考只用了 40 token，0.5 s 出答案）。
诚实边界：以上均为本卡（RTX 5070 Ti 16 GB）单机实测，题面为"数数字"语料——可预测输出下 dflash2 接受率高，换散文/开放问答解码会下降（约 160 tok/s 量级），draft 深度收益也随之变小。draft 12 在不可预测文本上可能不如 4，换任务时可回头对比一次。所有被拒配置（CUDA graph / 大池 / mtp+draft12）的拒绝原因都是引擎自己的启动期数字，非推断。
