为什么 641 MB？ 不是模型权重，也不是调试符号。fatbin 里是 完全模板展开后的 GPU 机器码： 同一套 GEMM 逻辑，对 bf16 / fp8 / nvfp4 / q4 / q5 / q6 / q8 / t2 八种权重格式， 乘以 gemm_mma / simt / splitk / ksplit / sliced_k / rowsplit 六七种调度策略， 再乘以具体的 N×K 形状常量（如 n248320_k5120）， 每个组合都是一个独立 kernel。实例数前三名：q8_a16_sliced_k_mma（888 个）、q8_ksplit_mma（405 个）、nvfp4_simt（270 个）。

它是"一个模型"还是"一族模型"？

两处硬约束说明它 只服务特定架构，不是通用引擎：

  • Qwen3.5 Program requires at least one full-attention layer —— 程序假设了「全注意力层 + 线性注意力层」的混合排布，这是 Qwen 3.5 系的结构特征。

03核心发现：三层 KV 与 KVMem 环

这是整个引擎最独特、也最值得理解的部分 —— 你项目里踩过的那些坑（超池丢中段、500 崩溃、前缀被挤）全部能在这里找到解释。

图 2 · 三层 KV 体系与两个争议旋钮

为什么"超池会静默答错"

引擎自己就把这个现象写进了一条超长告警，而且说得很坦白 —— 根因未定位：

// .rdata 原文摘录
Part of the prompt is therefore not resident, and the MIDDLE of such a prompt
has been measured to go missing with no error line, HTTP 200 and a plausible
wrong answer; the root cause is not localized.
Treat every answer to this request as unverified against its context, and raise
--kv-capacity to at least the prompt's token count.

这就是你笔记里「静默答错 = 超池中段丢失」的官方出处。它的机制现在也清楚了：Device 池装不下整段 prompt 时，中段页被降级到 Host；生成过程中需要它们时，由 Content Scorer 决定捞回哪些 —— 打分失手就悄悄少了几页，注意力直接少了那段上下文，但流程没有任何错误。

Content Scorer 的三个调参事实

ON 是默认，不是可选项

只要环开着，打分器就开着。设 NINFER_TERNARY_KVMEM_SCORE=0 会退回词法 IDF 排序 —— 作者明确称其为"负对照"，不是调优旋钮。

QUERY_TAIL 永远是 64

实测：池 4000、n=6 时，tail=256 只有 2/6，tail=64 有 6/6。作者原话「Never widen it」。加宽窗口等于把上一轮回答和填充文本也算进查询。

一个进程只能有一个序列。 打分器全局只维护一份 mean-K 索引和一份 raw-K 采样，两条活跃序列会互相把对方的块当成自己的来排序（源码位置都给了：mean_k_index.h:248-251）。所以环模式硬性要求 --max-concurrency 1。

05HTTP 接口：三套协议同时兼容

路由表显示它并不只是"OpenAI 兼容"，而是把三家协议都实现了一遍：

指标只有 8 个，但每一个都直指性能分析：

ninfer:prefix_cache_hit_tokens_total         // 前缀命中的 token 数 ← 你最关心的

07可直接落地的结论

按"对现有配置的收益"排序。这些都不需要改二进制，只是把已经存在的能力用起来。

最高优先 给 500 崩溃装一个安全阀

--recover-invariant-failures 的语义是：内部不变量破损时只失败当前请求、继续服务队列。你目前遇到的 Paged KV single-page materialization exceeds reservation 属于这一类 —— 加上它至少不用重启引擎。

注意：这是"带病继续跑"，不是修好。真正的修法仍是把 --max-shared-prefixes 改回 0。

值得试 用 Sink 钉住那 23k 的 tools 块

你的 <available_deferred_tools> 有 9,060 字符，整个 tools + system 前导约 23k token。在环模式下，这些页本来可能被降级再被检索回来 —— 而检索是打分器猜的。设 NINFER_KV_SINK=24000 左右，就能让它们永不被降级。

代价：池的工作余量会减少同样多的页。引擎启动时会算给你看，余量不足会直接报错并给出三条出路，不会静默失败。

省事 让引擎自己定容

--kv-capacity auto + --kv-headroom-mib N（别名 --vram-headroom-mib）可以让池按当时空闲显存自动定，不必手工二分。含义与 tools/probe-poolsize.py 做的事情一致，但由引擎原生完成，且会遵守硬三角。

风险：auto 的结果随桌面占用变化，跟你"参数固定可复现"的习惯相冲。建议只在换卡/换驱动后临时用一次来读推荐值。

诊断 打开统计面板与指标

--log-stats-panel on + --log-stats-interval-ms 2000 会在控制台打实时吞吐；/metrics 给出 8 个计数器，其中 prefix_cache_hit_tokens_total 和 draft_accepted_tokens_total 正好对应你最关心的两件事（前缀复用率、MTP 接受率）。

这是首次有了「不依赖客户端日志」的观测面。

调优 检索侧的两个新旋钮

NINFER_KV_RETRIEVE_SHARE（预算分配）与 NINFER_KV_NEIGHBOR_PAGES（邻页扩展）此前完全没进过你的实验清单。它们只影响"从 Host 捞回哪些页"，不改变池容量，属于低风险试验。

建议配合 kvmem_score: SELECT 那行日志观察 kept / sought / candidates 的变化。

关于"还能不能更快"

逆向给出的答案是：prefill 侧基本没有余量了。理由不是猜测 —— 二进制里有 354 个 cubin、按 N × K 形状特化到 n248320_k5120 这种粒度，意味着每种主流 tile 都已有手工 kernel；而 --prefill-chunk 的最优值 512 也是作者反复测过的（这条路径上还留着"2048 → 直接起不来"的痕迹）。剩下的空间在调度而不是算子：前缀命中率、KV 命中页的召回质量，才是真正的变量。
