加速实测报告 — A 组（引擎草稿/prefill）+ D 组（系统侧）

2026-10-12 · 引擎 ninfer-serve-120a.exe · 模型 gsq_rco_iq3_s_dflash2_prop.ninfer · RTX 5070 Ti 16 GB · 全部数据为同一次会话内实测

结论摘要

A 组：零收益
ngram 草稿调参不产生任何差异，不要改启动器。 两组语料 × 两配置共 4 次运行，decode 与草稿接受数在噪声内完全一致 （--ngram-min-match 8 + --lookup-ngram 32 对默认配置无改进）。 原因是 ngram 草稿默认就已经在满负荷工作。
prefill 512：装不下
tuned 档把 --prefill-chunk 提到 512 会启动即失败： 运行期需预留 1,199,772,160 B，而只剩 983,359,488 B。维持 256。
D 组：部分有效
电源计划已由「平衡」切到「高性能」；关掉 WidgetBoard / Intel Graphics Software 后 桌面独显占用 1320 → 973 MiB。但真正的大头 dwm（约 620 MiB 实际）挪不动。
更正
早前把 MuMu 与 GameViewer 当成独显主要竞争者，是错的。实测它们在独显上的占用 全部低于 20 MB 阈值，一个都没进榜。

读出来的三件事

  • 调参无差别：同一语料下两个配置的 ngram 接受数逐字相同（912/1,043 与 1,058/1,143）， 说明 --ngram-min-match 12 → 8、--lookup-ngram 0 → 32 没有带来任何新增草稿。
  • ngram 本来就在工作：复制型负载上 1,143 个 ngram 草稿中被接受 1,058 个（92.5%）， 这是默认配置的贡献，不是我们调出来的。
  • 负载类型比参数重要：同一套配置，复制型 351 tok/s 比生成型 275 tok/s 高约 28% —— 因为要输出的内容在 prompt 里已经存在，ngram 可以直接复制。 「让模型回显原文」的请求天生更快。

prefill-chunk 512 的失败原文

2026-10-12 12:05:34.601  ERROR engine init | FAILED while constructing the service:
  requested Engine runtime reservation requires 1199772160 bytes,
  but only 983359488 bytes are available for runtime capacity
2026-10-12 12:05:34.601  FATAL server failed during startup

差值约 206 MiB。tuned 档 --kv-capacity 8192 已把显存用满， prefill 块翻倍会多吃运行期预留，因此 256 是这张卡上的上限。不做改动。

留给你的可选项（未测）

  • --max-shared-prefixes 0 → 7 配合 --auto-prefix-grid：改善追问首字延迟，有显存代价。
  • --context-cache-policy rolling、--derive-session-keys：针对单会话不断增长的场景提复用率。
  • --kv-lease-growth：少预留、按需扩输出窗口，代价是池扩不动时答案会被截断。
  • 把显示器线插到主板 HDMI/DP：能一次拿回约 620 MiB，是所有手段里唯一能根治 dwm 占用的。
