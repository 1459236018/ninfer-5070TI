复用侧实测报告 — 前缀缓存 / 共享前缀 / 输出窗口

2026-10-12 · 引擎 ninfer-serve-120a.exe · 模型 gsq_rco_iq3_s_dflash2_prop.ninfer · RTX 5070 Ti 16 GB · tuned 档参数 · 全部为实测

结论摘要

启动器：一个字不改
之前列出的 5 个待测杠杆，4 个零收益、1 个有害。 现启动器里的 --max-shared-prefixes 0 不是疏漏，而是防御性正确配置—— 改成 7 会在长会话下把引擎打崩（见下）。本轮不产生任何启动器改动。
唯一的有效项，但危险
--max-shared-prefixes 7 在短 prompt（≤池）时能把跨会话 TTFT 从 1.0 s 压到 0.13~0.22 s（cache 98.2%，引擎标记 shared prefix）； 但在长 prompt（超池，正是你的 agent 会话）时 → worker crash / HTTP 500。 收益只存在于你不会用的场景，风险却落在你在用的场景。
根因：KV 池 = 8192 token
tuned 档的 --kv-capacity 8192 是本卡硬上限（16384 需 1.13 GB runtime， 只剩 0.98 GB，叠加 --kv-lease-growth 也一样失败）。 所以 prompt ≤ 8192 token 才有前缀复用；一超池，cache 直接归零、 TTFT 与 prompt 长度线性增长（25k token → 18.7 s）。 这才是 tuned 档跑长会话慢的根因，不是任何一个可调参数。

测法与脚手架

全部遵循「单变量对照 + 引擎日志自证」。日志里 req#N done 行自带 cache N (P%, 原因) | TTFT T，是复用问题的唯一判据。

脚本场景每轮问什么
runreuse.sh同一会话 4 轮「只增不减」追问prompt 每轮追加一问，观察第 2~4 轮能否复用
runshare.sh3 个不同会话共享同一段长 system 前缀首条 user 消息各不相同 → 派生出不同会话
run.sh1000 token 输出（数数字）看显存与吞吐是否被改动

实验前先证伪了一个设计错误：最初的测试 prompt 是 10k token， 比 8192 池还大 → 基线 4 轮 cache 全是 0。把 prompt 压进池内后才拿到有意义的对照。

③ 超池长 prompt — 同一项参数反而把引擎打崩

同一个 25,324 token 的 prompt（120,000 字符，远超 8192 池）， 发两个不同会话。唯一变量是 --max-shared-prefixes。

机制
开启共享目录后，引擎要把「稳定前缀」发布到共享目录 （frontier=25299、host_bytes=454 MB）；但池只有 8192，前缀根本装不下， 快照页不稳定 → worker 崩溃。这与已知的 NINFER_KV_REUSE_HOSTBACKED=1 是同一类坑： 都是「超池 + 前缀共享/adopt 机制」的组合触发。

⇒ 规律：超池本身不会崩；超池 + 任何前缀共享机制才崩。 所以前缀共享类参数只在 prompt ≤ 池大小（tuned 8192 / slim 17920）时安全且有效。

即便用 lease-growth 免去整个 max_tokens 输出窗口的预留， --kv-capacity 16384 仍差 157 MB 装不下 → 池 8192 是硬上限，无法通过参数翻倍。

⑤ 机制总结：复用能力完全由池大小决定

prompt 大小in tuned（池 8192）实测证据

建议（按代价从低到高）

  • 保持两个启动器不变。本轮 5 个候选项没有一个通过对本场景的性价比检验， --max-shared-prefixes 0 必须保留。
  • 别再试 --kv-capacity ≥16384、--prefill-chunk 512： 两者都因为运行期预留装不下而启动失败，已两次实测。
  • 想改善长会话体验，唯一有实际作用的杠杆是减少超池—— 即收敛单次会话的历史长度与工具数量（把 52k token 压回 8k 以内， 追问就能从 18.7 s 掉到 ~105 ms；这个落差是 170 倍，远大于任何参数微调）。
  • 长会话也可以改用 slim 档（池 17,920 是 tuned 的 2.2 倍）， 用 37% 的 decode 速度换更宽的前缀复用窗口。
