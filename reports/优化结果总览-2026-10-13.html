根因已定位
「时不时要等 30~50 秒」不是算得慢，而是前缀缓存被超池摧毁：引擎只在整段 prompt 装得下池时才保留检查点， 一旦超过，已存检查点被丢弃，之后每一轮都从零全量重算。实测超池仅 178 个 token 的那轮仍能复用 75.9 %， 下一轮直接归零。所以是「超一次，后面全慢」。

有意的取舍

三个关键机制

① 超池 = 缓存归零（不是「慢一轮」）

引擎的检查点必须整段装进设备 KV 池。实测某轮超出池仅 178 个 token 时仍复用 75.9 %， 但下一轮就归零——因为那个检查点已经装不下池、被整个丢弃。这就是为什么用户体感是 「时不时」而不是「偶尔」：超一次之后，整段会话都跟着退化，直到客户端压缩历史。

prompt 涨过池→ 检查点被丢弃→ 之后每轮从零 prefill→ TTFT 与 prompt 长度成正比

② --cuda-graph-allowance-mib 才是池容量的真闸门

引擎帮助原文：这个额度是 从 KV 预算里扣的（taken from the KV sizing budget）， 默认值按 profile 自动计算，实测会默默占掉约 0.7 GiB 的 KV 预算。 显式压到 128 MiB 后，同一块卡上的池上限从 69,632 直接抬到 98,304 —— 而且 decode 速率一点没退化（170.3 / 167.9 / 163.7 vs 170.6 / 168.2 / 164.3 tok/s）， 1024 token 的长输出也跑得干净。现取 81,920，把空闲显存从 359 MiB 留回 657 MiB。

红线（改参数前必看）

必守
--derive-session-keys 不能删。只开共享前缀目录而不配它， worker 会崩（实测两种崩法：active KV snapshot full page is not stable ／ page ownership is not ordered）。这是硬依赖，不是可调项。
触发条件
prompt 一旦超过 KV 池，之后任何共享前缀复用都会崩引擎：Paged KV single-page materialization exceeds reservation（HTTP 500，随后 503）。--context-cache-policy rolling 挡不住，--host-state-slots 0 虽不崩但共享前缀彻底失效（命中率 0 %）。 所以池必须覆盖真实峰值——这就是把池做成 81,920 而不是停在 69,632 的第二个理由。
出事了怎么办
先把 --max-shared-prefixes 改回 0，再考虑抬 --kv-capacity， 不要往上堆别的缓存参数。若只是「点图标起不来」（托盘变红、20 秒自退）， 把池退到 73,728（空闲回到 874 MiB）即可，不必改别的。
量化余量
池 81,920 对你的真实负载：文本峰值实测 68,101 token，一张 1080p 截图实测 2,104 token （真机 1920×1080 PNG）→ 还能再放约 6 张图。

已证伪清单（不要再试）

尝试结论
--fast-prefill-kernel与基线逐项相同，零收益
--prefill-chunk 1024 + --prefill-cublasprefill 仅 +6 %，多占 500 MiB
NINFER_KV_REUSE_HOSTBACKED=1不崩但缓存仍为 0
--use-alt-prefix-caching与 ring / host-kv / 共享前缀互斥，并要求池 ≥ max-context，本卡不可达
--auto-long-anchors + rolling + --thorough-admission-search + --release-diverged-checkpoints超池下零改善，且必崩（HTTP 500 → 503）
--context-cache-policy rolling（用于防超池崩）挡不住，仍崩在同一个 materialization 断言
--host-state-slots 0不崩了，但共享前缀命中率归零 —— 不是解
--kv-capacity auto极度保守，只给 17,536 token，不如写死
借用「共享 GPU 内存」扩池机制不可用：那是 WDDM 给 D3D 程序的溢出池，引擎走 cudaMalloc 只落专用显存； 硬证据是差 17 MB 那档直接启动失败而不是借用起来。且带宽差约 35 倍（25 vs 900 GB/s）
用 NPU 参与加速引擎纯 CUDA（只链 cudart / cublas），模型是私有格式，无法接入
